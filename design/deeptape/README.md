# 深流随身听 / DEEPTAPE · 第四版：入水播放与被救援者舞步

已接入游戏。通过本机服务打开 `game.html` 是完整游戏的浏览器适配版，点击主菜单「一键下潜」，不经过营地。页面外的「评审：查看相遇」只用于快速移动到目标附近并重播手记，没有加入微信游戏。浏览器存档使用独立命名空间，不接触微信存档；音乐、游戏逻辑与渲染均使用源代码，云端环境音和一次性音效仍由微信端提供。

`index.html` 保留分层试听、HUD 和角色样例；点击「完整旅程」约 32 秒走完五层累加、发现与返程。

## 概念

玩家最初看到的是一台被潜水员带进洞穴的旧防水随身听，以为音乐来自磁带。寻找时「向深处去」，发现时「就在这里」，绑好救援绳后翻到 B 面「一起回去」。距离控制配器的丰盛程度，120 BPM 的共同速度保持不变。

开发设定：音乐实际上是受困者尚未说出口的心声。随身听只是玩家最初的解释，不是高科技探测设备，也不是主角自己的背景音乐。现阶段不在台词、HUD、预览文案中揭示这个答案。

实体设计统一为暗色圆角外壳、米白纸标签、暗红横条、双卷轴与下方压带结构。倒带、入水播放、HUD、胸前磁带全部调用 PaperCassette；小于 120px 时仅简化渐变与细字，保留同一外形、色彩和卷轴布局。没有引入位图资源。

色彩是珊瑚橙（寻找）、酸橙黄（发现）、薄荷绿（返程），搭配纸白文字。游戏内氧气环、驾驶模式、音量、深度标牌、浮力控制器外壳、背包条与提示框采用共同的纸白/深墨/切角语言。危险提示仍由氧气、深度、减压的真实状态控制。

默认 HUD 只画一台磁带，不再显示侧边分层条或层数文字。短按查看提示，按住才展开封套；松手后收起。下潜界面和角色装备是重构重点，商店与图鉴等页面没有整站改版。

## 入场流程

主界面直达 → 磁带倒带 → 入水转场 → 水下按下 PLAY → 音乐起音 → 取得控制。

倒带等待十二条循环轨、pickup 与音频上下文就绪。卷带量和倒数计数器表示磁带的位置；缓存已就绪时仍完成约 0.7 秒的机械动作。准备失败或音频未解锁时保持在倒带页，可重试或返回，不会悄悄进入无音乐的游戏。

入水后的播放演出先让运输键落下，再允许音频引擎启动；只有可听输出时钟已启动，才解锁操作、氧耗、鱼与下潜计时。磁带旁短暂出现纸签「NOW PLAYING / SIDE A · 夜航」，4.2 秒后完全消失。默认不常驻侧边说明，不使用通用居中文字提示。

BCD 控件与浮力、氧耗、边缘告警颜色保留；首次可见教学、深度教学、上浮/下沉过快的文字处置提示移除。

## 节拍对应

| 声部 | 视觉 |
| --- | --- |
| 底轨主题 | 磁带盘随共同音乐拍位转动 |
| 01 微光 / beacon | 原乐谱信标起音点亮第一条光带；弱回应使用较弱亮度 |
| 02 低流 / bass | 低音起音点亮第二条光带、轻推磁带轮 |
| 03 重鼓 / drums | 真实底鼓让全身短促舒展、倾身、肩臂打开，胸口微光回应；支持 C 版切分 |
| 04 疾行 / arp | 胸前微光的回应更清楚，每个八分音符推进封套内的第四条光带 |
| 05 奔涌 / spark | 更明显的全身舒展、肩臂张开；每 50ms 一个疾奏音符逐格推进磁带窗口 |

每个声部独立表现，全身回应由鼓点驱动，疾奏逐格推进磁带窗口。角色周围的光流、轮廓线、光屑和入层绽放已移除，反馈集中在角色姿态、胸口光点与随身听，身体外侧的弧形描边也一并移除。

被救援者使用八拍舞句：左右指天与叉腰、双手举起、摆肩、屈膝交替换脚。鼓点驱动蹲弹和压缩，反拍驱动肩臂。舞句始终读取同一个可听音乐拍位，画外就已经在跳；入镜时不重启动作，救援绑绳后恢复游泳跟随。身体入镜预判包含举手、脚蹼和横移幅度。

舞步只改变绘制姿态，不改碰撞体、移动速度、救援距离或镜头。停止后回到原角色表现；静音仍保留音乐时间与舞句，去掉声部击点反馈。

## 单一伏笔与舞步合理化（开发说明）

1. 随身听没有注明收录者。长按封套里保留一截旧胶带，写着「听不清，就再近一点。」初见可以当成普通的随身听留言，后续又可以理解成对人的话。
2. 先听见音乐，再发现被救援者一直在踩着同一节拍跳舞。以动作建立音乐与他的关系，不给方向箭头、不标记声源，也不在画外透露他的位置。
不在 Loading、磁带正面、入口或第一晚日常剧情重复暗示。仅保留长按封套里的旧便签，曲名改为中性的《夜航》。

第一次看见被救援者时，以短暂的「潜水手记」呈现观察：「他似乎认不出这里了。把洞穴当成了舞池，还在笑。得先把他带回水面。」设定为困境中意识状态异常，重复熟悉的舞步；观察者不作具体病理诊断，不提前解释音乐为何与他同步。手记出现一次，八秒后收起；绑绳后提前收起。

被救援者在迷宫的光照遮罩之后绘制一次，保留低饱和暖色和浅色装备，因此只要身体入镜就能辨认姿态；不依赖手电照射，不添加外部光圈，也不照亮周围洞穴。画外不显示位置或提示。

未来揭示的落点：被救者无意哼出同一段句尾，玩家再回想这些细节。这里仅记录后续叙事方向，不提前实现揭示对白。

## 同步实现

旧光圈依赖 `lastPulse < 0.5 && pulse >= 0.95` 捕捉上升沿。普通渲染帧很容易错过峰值，后段就出现「音乐在响，波纹没触发」。

现在 `AdaptiveMusicVisuals` 直接从 `notesFor()` 的同一份乐谱取得每个声部的实际起音，按音频输出时间查询当前音符位置、距起音的时间和短包络。动画不积累帧时间，不设置自己的 BPM，不用 FFT 分析窗，也不等待阈值触发。掉帧后直接落到正确音符，短尾迹保留经过的格位。

`AdaptiveMusicEngine.getClock()` 同时输出可听拍位、实际混音增益、版本与状态。切层在原音乐入口开始；视觉亮度随同一条增益曲线淡入淡出，包括第五层展开和返程收束。可用时采用 `getOutputTimestamp()` 对齐扬声器输出，兼容实现使用上报的 `outputLatency` / `baseLatency`；不支持这些接口时使用原音频时钟，不猜测设备延迟。

## 验证与边界

- `npm run visuals:check`：A/B/C × 寻找/发现/返程的全部主要声部实际起音；每轮 320 个疾奏音符在 30/60/120fps 与不同采样偏移下逐一更新；长时间循环、C 版切分、切层与增益包络、输出延迟、挂起与重启；默认仅磁带、真实 HUD 静止长按、松手、短按；五级与四级全身姿态差异、静音/停止恢复自然姿态。
- `npm run audio:check`：现有全部音频与救援流程回归通过，音乐内容、响度与编排未修改。
- `npm run platform:check`、`npm run typecheck`、`npm run build` 通过。
- 浏览器完成真实音频播放、发现与返程切换、完整旅程、停止与三版本切换检查。
- `game.html` 使用完整游戏逻辑与原生音乐合成；`index.html` 的洞穴轮廓、深度/氧气数值、呼吸与减压服务仍是场景样例。
- `scripts/checkTapeEntry.js` 检查准备/失败/解锁门禁、入场冻结、按键后才放行音乐、可听时钟启动后才取得控制、八拍舞步、曲名退场及 BCD 文字消失。
- 微信真机的扬声器/蓝牙链路尚未实测。视觉展示受屏幕刷新率约束，不能保证低于 20fps 时仍单独显示每个 50ms 音符；此时光带直接追到当前格并保留短尾迹，不会积压动画。
